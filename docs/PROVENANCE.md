# Future run provenance

New sandbox builds record `applicationSourceHash`: SHA-256 over every file in the allowlisted shared application context, before adding its generated Dockerfile. That context contains the exact compiled checkout application (including its maps), root package manifest, workspace manifest and lockfile copied into the build. Each sorted relative file name, NUL separator, exact file bytes and final NUL contributes to the digest. Variant policy hashes remain separate. This records the shared application inputs that were missing from historical manifests; it does not substitute a current source-tree hash for the application image that actually ran.

The manifest also records the copied lockfile hash, candidate SDK source hash and planner build-context hash. Immutable Docker image IDs identify the resulting node, PostgreSQL, candidate, planner and four application images. Build and runtime metadata are complementary: source hashes alone do not establish equivalent images or behavior.

Before new verification runs, the controller validates and writes `environment.json.provenance`. It includes the shared application and component hashes, current host controller/judge source hashes, current lockfile hash, Git commit and dirty status, immutable image IDs, PostgreSQL mode, concurrency and fsync setting. The current runtime requires fresh `initdb`, fsync on and concurrency 1–3. Changed lockfiles or manifests missing build provenance require a new sandbox build. Historical manifests remain readable; their absent fields are never inferred or backfilled.

Host source hashing uses exact bytes and sorted repository-relative file names. Controller coverage includes CLI, runtime, Sentry, MCP, contracts, telemetry and scripts. Judge coverage includes the judge, contracts, telemetry and the candidate broker SDK. Test files are excluded; executable TypeScript/JavaScript, JSON and shell files are included. These hashes describe the trusted host source at collection time, not a defense against a malicious host or edits made while a process is already running.

Git status includes tracked modifications and untracked files, respecting normal Git ignore rules. Source archives without their own `.git`, unavailable Git executables and failed Git reads record `status: UNAVAILABLE`, `commit: null`, `dirty: null`; they never inherit an unrelated ancestor repository's commit or claim a clean checkout. Source hashes remain available for such archives.

The measurement wrapper retains the saved environment, and the publication projection accepts new provenance only through its strict schema. The projected fields contain validated hashes, image IDs, timestamps, fixed enums and booleans; they contain no source contents, arbitrary paths, credentials or raw Git output. Existing historical measurements and their interpretation remain unchanged. No new performance comparison is implied by adding this metadata.
