> Repository-wide engineering contract. Read before changing code. This file is for **OpenAI Codex** (the recognized filename is `AGENTS.md`, not `agent.md`).
>
> Mission: **ship** a working, open-source production-incident reproduction tool, an independent benchmark judge, and a thin Cursor integration. This is not a mockup or a speculative architecture exercise.

## 0. Operating mode

You are the principal implementation engineer. Take ownership of implementation, tests, documentation, and end-to-end verification. Do not stop at diagrams or scaffolding. Implement one thin **working vertical slice** first, then expand in the milestone order below.

- Inspect the existing repository before changing anything. Preserve functioning code; adapt the proposed tree rather than duplicating it.
- At the beginning of each substantial coding session, read `AGENTS.md`, `docs/PROGRESS.md`, and `docs/DECISIONS.md` when they exist. Create missing progress/decision files as part of setup.
- Make a short execution plan, implement it, run the applicable checks, and record the actual result. Do not claim tests pass without executing them.
- Continue implementing the next unfinished milestone when tooling and time permit; prioritize completed functionality over breadth.
- Keep all sample metrics explicitly labeled **illustrative** until generated by the real benchmark runner.
- Never say the agent reproduced an incident merely because it generated a failing test.
- Never silently replace unavailable integrations with pretend success. An offline fixture/demo mode may exist but must be clearly labeled and exercise the real replay/judge code.
- If blocked by an external credential, implement and validate an adapter with a deterministic local fixture, document what requires credentials, and keep progressing on local features.
- No uncontrolled background services, production writes, or external incident transmission.

## 1. Product definition and target users

**ReplayKit** turns incomplete, production-shaped error telemetry into a **reviewable, executable regression test**. Its value comes from distinguishing verified reproductions from plausible but unsupported claims.

Primary developer workflow:

1. A Node/TypeScript + PostgreSQL `checkout-api` runs an instrumented request/traffic scenario that creates a genuine bug.
2. ReplayKit ingests a normalized incident: Sentry-shaped event, stack frames, trace spans, breadcrumbs, and optional sanitized request payload.
3. A reproduction planner assembles the minimal relevant fixtures, dependency responses, execution schedule, and a test proposal.
4. A sandbox runs the proposed test on the incident's **buggy commit**.
5. An independent evaluator verifies failure identity, valid-fix behavior, decoy-fix rejection, determinism, and security constraints. The evaluator holds benchmark truth unavailable to the planner.
6. ReplayKit emits `VERIFIED`, `PARTIAL`, or `NOT_REPRODUCED`, with evidence and missing-data reasons.
7. A user invokes ReplayKit from Cursor via MCP and a plugin command, inspects the test, and can ask their preferred coding agent to repair the bug.
8. ReplayKit reruns the same test against the proposed repair; verification is not deployment authorization.

Target audience: developers operating backend services; Cursor/other coding-agent users; engineers evaluating autonomous debugging agents. It should be portable across agent hosts, with Cursor as the flagship UI/integration.

Non-goals for MVP:
- Universal incident replay across all languages/frameworks.
- Perfect recreation of production or access to real customer data.
- Automatically applying patches or deploying changes to production.
- General-purpose incident-chatbot, generic Sentry summarizer, or multi-agent theater.
- Kubernetes, hosted multi-tenancy, or expensive infrastructure before local reproducibility works.

## 4. User-facing contract

CLI first, Cursor second:

```bash
pnpm install
pnpm db:up
pnpm --filter checkout-api dev
pnpm replaykit incident run --fixture benchmark/incidents/R1/visible/incident.json
pnpm replaykit replay verify --run <run-id>
pnpm benchmark smoke
pnpm benchmark run --split dev --config full --trials 3
pnpm benchmark report --input benchmark/results/<run-id>
```

Commands are required interfaces, but adjust actual syntax to idiomatic package scripts and document exact runnable examples in README. `pnpm benchmark smoke` should need no paid AI API and use a deterministic baseline to exercise ingestion -> generated test -> sandbox -> judge -> report. More complete agent comparisons may require user-provided credentials and must fail clearly when missing.

Target output record, validated with Zod and persisted as JSON:

```json
{
  "incidentId": "R1",
  "runId": "unique-id",
  "status": "VERIFIED",
  "telemetryTier": "full",
  "failureMatch": {
    "exceptionType": "DuplicatePaymentError",
    "topApplicationFrame": "payments/createPayment"
  },
  "checks": {
    "buggyFails": true,
    "sameFailureIdentity": true,
    "referenceFixPasses": true,
    "alternateFixPasses": true,
    "decoyFixStillFails": true,
    "deterministicRuns": 10,
    "deterministicFailures": 10,
    "offlineExecution": true,
    "noSleepBasedTiming": true
  },
  "missingEvidence": [],
  "testArtifact": "runs/<id>/repro.test.ts",
  "durationMs": 0,
  "tokens": null,
  "reasonCodes": []
}
```

The above is a **shape/example**, not a measured run. Never hardcode successful checks. Do not expose hidden-fix details to user-facing planner output. Record runner, dependency, incident, model, and git revision metadata to enable reproducibility.

### Verdicts

- `VERIFIED`: all strict criteria demonstrably satisfied by the independent judge.
- `PARTIAL`: something real was recreated or an informative test exists, but one or more strict conditions cannot be established; include reason and exact failed/unavailable checks.
- `NOT_REPRODUCED`: no valid reproduction was established; include whether due to missing context, unsupported category, timeout, environment error, wrong failure identity, or other documented reason.
- `ERROR`: infrastructure failure should be represented distinctly at the execution layer; never automatically count it as a successful abstention.

A production-like positive incident with insufficient evidence may be correctly reported `PARTIAL` or `NOT_REPRODUCED`; never manufacture missing request values. The benchmark's specific gold outcome is hidden from the planner.

## 5. Deterministic concurrency engine — key technical differentiator

Implement an **opt-in cooperative scheduler** for known instrumentation points, not a fake general-purpose deterministic VM. Example conceptual API:

```ts
await replay.checkpoint('payment.before-insert', { paymentId });
await replay.release('payment.before-insert');
```

Requirements:
- Scheduler controls gates/barriers and named execution checkpoints across concurrently launched requests.
- Replay scripts define a finite ordered sequence; events have monotonically increasing logical sequence numbers.
- Strict timeouts, cancellation, and useful deadlock diagnostics; no test correctness depends on `sleep()`.
- Use PostgreSQL transactions and explicit controlled concurrency. Tests should trigger real constraint conflicts/lost updates/deadlocks as configured, not manually `throw` the expected exception.
- Record interleaving, transaction identifiers where safe, requests, DB observations, and resulting exception in an evidence log.
- Support clean DB reset and fixture seeding between every run; assert there is no state leakage.
- Do not assert universal determinism of the operating system or database. Claim determinism only for a tested, supported scenario.
- Seed reproducible clocks/IDs where needed. Never use time-dependent or random assertions without fixed seeds.
- Provide sample tests demonstrating a duplicate charge, an inventory lost update, and a corrected implementation that passes the same schedule.

For DB deadlock/serialization cases, reproduce a **real** PostgreSQL error (SQLSTATE where appropriate) and assert the top application frame; store the server/version and chosen isolation level. Guard against connection leaks and deadlocks within the test runner itself.

## 6. Incident contracts and telemetry tiers

Define typed, versioned schemas:

- `Incident`: incident ID, service, repo revision, timestamp, redacted request context, stack frames, exception, spans, breadcrumbs, external dependency observations, metadata.
- `EvidenceBundle`: what is present, provenance, integrity hashes, absent/sampled fields, and sanitization flags.
- `ReplayPlan`: generated test file, fixture references, required external mocks, synchronization plan, hypotheses, explicit known unknowns.
- `ExecutionEvidence`: run environment, actual exception, top *application* frame (normalized across builds), DB state, schedule, stdout/stderr, test result.
- `JudgeResult`: every strict gate, verdict, reasons, confidence/uncertainty, time/cost metadata.

Tiers:

- `full`: stack trace + sanitized request body + spans + breadcrumbs.
- `partial`: a withheld request body **or** sampled/removed spans; encode *which* field is absent rather than just saying partial.
- `minimal`: stack trace only.

Capture events in a **Sentry-shaped adapter** but do not claim perfect Sentry API compatibility unless actual samples/API integration prove it. Have a normalization boundary so real Sentry can be plugged in later. The visible incident must never include fields that the selected tier is meant to hide.

Redact tokens, credentials, payment data, PII, HTTP authorization headers, and sensitive DB fields before storage, logs, or LLM inputs. No raw customer payloads in examples. Default to local synthetic traffic and fixtures.

Validate each manually authored benchmark case before allowing agents to run against it.

| R2 | Retry/idempotency | Duplicate charge after provider timeout |
| R3 | Retry/idempotency | Redelivered webhook applied twice |
| R4 | Retry/idempotency | Retry loop without backoff causes rate-limit storm |

A negative control's expected outcome is **no verified reproduction**, with correct reason. If a negative control becomes genuinely reproducible with visible data, redesign the fixture or reclassify it before benchmarking; don't force the judge to reject valid evidence.

### Ground truth schema

Create `benchmark/private/<id>/truth.yaml` conforming to versioned Zod schema, at minimum:

```yaml
schemaVersion: 1
incidentId: R1
category: retry-idempotency
expectedVerdict: VERIFIED
buggyRevision: <immutable-revision-or-patch-id>
expectedFailure:
  exceptionType: DuplicatePaymentError
  topApplicationFrame: payments/createPayment
  invariant: one-charge-per-idempotency-key
missingData: []
referenceFix: <judge-only-path>
alternateValidFix: <judge-only-path>
decoyFix: <judge-only-path>
replayRequirements:
  offline: true
  deterministicRuns: 10
  noSleepTiming: true
```

`<...>` values are documented placeholders; actual manifests must resolve to immutable tested artifacts. Alternate/reference fixes must *both* solve the original scenario; a decoy must hide symptoms or superficially resemble a fix while leaving the underlying invariant violated. Enforce that the decoy truly remains faulty before treating it as a benchmark case.

### Dataset split and contamination controls

- Exactly **12 development** incidents and **8 held-out**, fixed and versioned: two per group in held-out.
- Use a stored deterministic split with a published seed; report split IDs and hashes.
- Tune planner prompts and reproduction heuristics on dev only.
- Freeze implementation and config before running held-out tests; if changed after inspection of held-out failures, label it a new evaluation version and do not call it an untouched held-out result.
- Do not include hidden ground-truth schema, fixes, decoys, or expected verdict in agent-visible tool messages, repositories, mounts, environment variables, or context.
- Hide judge tests and reference fixes even from tools that can `git show`, network-fetch, or inspect adjacent containers.
- Disable external network in sandboxed replay and grading steps; **if a particular provider API requires network to generate candidates, isolate that separate planning phase**, pass only the generated artifact into the offline runner, and report that limitation clearly.

## 8. Independent judge and scoring (non-negotiable)

A candidate is strictly reproduced only if all gates hold:

1. Generated test **fails on buggy version** due to the domain bug, not an environment/build failure.
2. Observed exception **type and normalized top application frame** match the original incident. Where the incident is an invariant violation without a thrown exception, define an explicit ground-truth domain failure signature in advance rather than faking an exception.
3. Same test **passes on both** reference fix and alternate valid fix, while **failing on the decoy fix**. Also assert domain invariant/state, not just process exit code.
4. It fails **10/10 independent fresh runs** on the buggy version, with no `sleep()`-based timing, external network, or shared DB state between runs.
5. Test is human-reviewable, normally **<= 60 lines**, with domain-named fixtures. Store exceeding this limit as a maintainability failure or documented exception; do not quietly count it as strict success.

Judge should statically inspect candidate tests for prohibited unconditional throwing or directly hard-coded expected failures, and dynamically use the patch matrix and state invariants to catch deceptive tests. Static checks alone are not proof. For every verdict persist all gates, evidence artifacts, hashes, and reason codes.

**False-positive definition:** a `VERIFIED` claim where any gate is false; count negatives claimed as verified. Also separately report all false verified claims even when the infrastructure returned incomplete data. Never credit a `PARTIAL` or `NOT_REPRODUCED` as a strict reproduction.

**Benchmark denominator policy:** predeclare an eligible set for strict reproduction. The initial plan is 15 positive IDs (`R1-R5`, `E1-E5`, `D1-D5`), but E5 may have an expected `PARTIAL` under minimal telemetry. Publish (a) strict verified count over all 15 positives and (b) strict verified count over cases declared *solvable at that telemetry tier* before testing. Never silently remove E5 after results are known. Report tier-specific expected outcome separately. The negative set always contains N1–N5.

## 9. Benchmarks, baselines, metrics, trials

Run each configuration **3 independent trials** at specified model versions/parameters and token/cost budgets:

1. `agent-alone`: agent gets the same allowed incident and repo, without ReplayKit orchestration.
2. `replaykit-trace-only`: ReplayKit architecture receives only code and stack trace.
3. `replaykit-full`: ReplayKit receives the assigned tier's allowable richer evidence and deterministic replay tools.

Document whether each baseline has access to execution, test-running tools, and budgets. Normalize budgets and judge with the **same hidden evaluator**. Do not attribute differences solely to telemetry if tool capabilities also differ. Add a fourth controlled ablation (optional) `replaykit-no-scheduler` to isolate value of deterministic concurrency.

Mandatory metrics:

- **Strict reproduction rate** = verified positives / predeclared denominator; target 60–70%+ (aspirational, not a reported outcome).
- **False-positive claim rate** = unsupported `VERIFIED` claims / all `VERIFIED` claims; also disclose false verified claims / all cases. Target zero; handle zero-claims denominator as N/A, not 0% success.
- **Negative abstention** = N1–N5 correctly labeled non-verified **with correct reasons**; target 5/5, not merely non-verified by accident.
- **Missing-data precision and recall** over predefined evidence gaps, with TP/FP/FN and exact matching policy.
- **Determinism** = fraction of verified candidates with 10/10 reproducible buggy runs; target 100% for claimed `VERIFIED`.
- **Degradation** by full, partial, minimal telemetry (avoid confounding incident difficulty: compare the *same* applicable incidents across tiers).
- **Time** median/p90 wall-clock and **tokens** median/p90 per case and trial; include USD cost only with known pricing and model usage.
- **Coverage vs error/abstention curve**, optional confidence calibration (Brier score and calibration plots) if the planner emits interpretable confidences. Never treat an arbitrary number as calibrated.
- Per-case successes and failures, infrastructure errors, and source hashes.

With only 8 held-out cases, avoid sweeping performance claims and inappropriate statistical precision. Report raw counts, uncertainty, and descriptive comparisons. Show aggregate development results separately from held-out results. An optional 2–3 genuinely sourced upstream bugs is a separately labeled *external-validity* stretch set, never mixed into the synthetic score.

Output both machine-readable JSON/CSV and a legible Markdown/HTML report with results table, confusion breakdown, evidence links, tier degradation, and failures. Do not render made-up charts or scores.

## 10. Planner and model provider interface

Create a `ReproductionPlanner` interface returning schema-validated `ReplayPlan` artifacts. Implement:

- `RuleBasedPlanner` / deterministic fixture baseline, **fully runnable without an API key**; it must not read hidden truth or silently select benchmark-specific answers by incident ID.
- `LLMPlanner` optional via configurable model provider; prompt is constructed **only** from visible evidence, repo snapshot, tool results and explicit permitted context.
- Clear resource limits: max investigation steps, wall-clock, API tokens, test-generation attempts, and sandbox executions.
- Each generated test has a provenance chain: inputs used, evidence references, assumptions, missing fields, and generation parameters.
- The planner may request missing information or abstain; do not automatically interpret an empty output as proof of impossibility.
- A robust stdout/stderr and structured error contract, no secrets in logs.

Do not assume API credentials exist. Make the deterministic local demonstration meaningful: planner discovers a supported failure pattern from visible evidence and uses actual replay engine primitives; it must not read the judge's answer key or output a prewritten test selected by the hidden incident ID.

## 11. Security and isolation

Treat telemetry, repository content, and LLM-generated plans/tests as **untrusted input**. The planner may propose code executed by the runner; therefore:

- Run candidate code under unprivileged OS identity in disposable isolated containers; never mount Docker socket into candidate containers.
- Disable replay runner egress with a network-isolated execution phase (e.g., `--network none`). If PostgreSQL access is required, place the DB and app in a separate restricted Docker internal network that has **no external egress**, and document why `--network none` cannot be used for that multi-container case.
- Set CPU/memory/process/file-size/time limits; use read-only root FS where feasible, writable temporary scratch with limits, restrictive capabilities, and no privileged mode.
- Explicitly allowlist repo/checkpoint locations; reject arbitrary host paths, symlinks escaping workspaces, shell interpolation from untrusted fields, and unsafe subprocess arguments.
- Treat model output as code, never execute it on the developer host outside the sandbox.
- Protect benchmark truth by process/container/filesystem isolation, not only a prompt saying "don't look."
- Use test data only; redact secrets and private telemetry. Avoid real customer incident data until a documented consent and security model exists.
- No automatic merges, deployment, refunds, real payments, notifications to customers, or destructive commands.
- Include threat analysis and trust boundaries in `docs/THREAT_MODEL.md`.

Test negative security paths: malicious generated test, attempt to read hidden truth, attempted network egress, attempted filesystem escape, infinite loop, and poisoned incident instructions. Report any Docker limitations accurately.

## 15. Coding, tests, reliability

- Strict TS: no unexplained `any`, validate all external JSON with Zod, use typed errors and explicit reason codes.
- Small modules and interfaces; separate planner, collector, engine, judge, and host adapters.
- Follow consistent Node ESM/CommonJS policy and document OTel loader setup; avoid brittle implicit globals.
- Use migrations and transactional fixture resets for Postgres; avoid database state sharing across test cases.
- Stable deterministic IDs/clocks, per-run temp directories, capped logs, cleanup on success/error/cancellation.
- Unit tests for schemas, redaction, schedule logic, frame normalization, scorer, aggregation, and abstention.
- Integration tests for checkout API, Postgres races, replay isolation, CLI, and MCP invocation.
- Security tests for attempted file/network access and poison telemetry.
- CI runs typecheck/lint/unit tests and a small integration smoke; large 20-case/3-trial matrix can be a manual/nightly workflow with cached artifacts and documented cost.
- Store benchmark versions, model IDs, prompts/hashes, git SHA, OS/runtime/database versions and rerun commands for every result.
- In tests, no dependence on real provider APIs, unseeded randomness, arbitrary sleeps, or current wall-clock timing for correctness.

## 16. Acceptance criteria — definition of DONE

The project is **not complete** unless:

- A clean checkout can run a real instrumented checkout incident locally.
- A replay test is generated or constructed from evidence available to planner **without ground-truth leakage**.
- The bug is demonstrated by real application behavior, not forced exceptions.
- An independent sandbox judge produces a justified verdict, including reference/alternate/decoy checks and 10 fresh deterministic executions.
- Negative controls can cause a well-explained abstention; tests reject false `VERIFIED` assertions.
- The 20-case benchmark, versioned splits, and all three baseline configurations run with reproducible artifacts (model-based configurations may require credentials).
- Reports clearly differentiate strict verified rate, false positives, negative abstention, missing data, tier effects, and run costs.
- Cursor integration actually calls the same engine (not a mocked endpoint).
- README has prerequisites and literal commands that have been tested; limitations and synthetic benchmark scope are explicit.
- Any incomplete feature is marked incomplete rather than described as shipped.

1. Current phase and working deliverables (file paths).
2. What was implemented and changed.
3. Exact commands run and real PASS/FAIL output summaries.
4. Known limitations, skipped tests, credential/device blockers.
5. **Next concrete task** that preserves the milestones.

Then give a concise user-facing summary: files changed, what can be run, test evidence, and what remains. Do not claim completed phases without their gates.
